# Language wrappers — overview and architecture

Five language-flavoured wrapper headers sit on top of the C value layer and the
assembly emitter, each re-expressing a signature feature set of a real language in
x64: **Rust, C++, C#, Python, and JavaScript**. This document describes the shared
architecture; each language's full reference is its own `*_interface.md`:

| Language | Header | Driver | Reference |
| --- | --- | --- | --- |
| Rust | `rust_funcs.h` | `rust_main.c` | [`rust/rust_interface.md`](../rust/rust_interface.md) |
| C++ | `cpp_funcs.h` | `cpp_main.c` | [`cpp/cpp_interface.md`](../cpp/cpp_interface.md) |
| C# | `csharp_funcs.h` | `csharp_main.c` | [`csharp/csharp_interface.md`](../csharp/csharp_interface.md) |
| Python | `py_funcs.h` | `py_main.c` | [`py/py_interface.md`](../py/py_interface.md) |
| JavaScript | `js_funcs.h` | `js_main.c` | [`js/js_interface.md`](../js/js_interface.md) |

## 1. The layering

Each wrapper is a **thin planner** over the two lower layers, adding no new output
path:

- `asm_funcs.h` — the MASM x64 emitter: `AsmDataField {location, tag}` cells, the
  local + global tag dictionaries, `write_proc`/`write_endp`, `write_*_call`,
  `write_if_*_then_jump_to`, the semantic moves, and the struct-layout helpers.
- `c_funcs.h` — the value / register-allocation layer: `CType`, `CValue`, `CFunc`,
  `CStruct`, `c_begin_function`, `c_param`, `c_call*`, `c_if_*`, `c_add`, … (see
  [`../c/c_interface.md`](../c/c_interface.md) and [`../c/c_architecture.md`](../c/c_architecture.md)).

A language wrapper decides *what the language semantics are* — moves, refcounts,
vtables, boxing, tagged values — and lowers them to `c_*` / `write_*` calls. **No
wrapper emits raw text**, so every generated byte still flows through the emitters
and stays validated by the type-tag dictionaries; a lowering mistake surfaces as an
ordinary generation-time abort.

## 2. Shared design principles

Every wrapper honours the conventions of the layers beneath it, which is what keeps
the generated programs validated and readable:

1. **Paired open/close returns a descriptor the closer consumes** — e.g.
   `rust_fn_begin(...) -> RustFn` → `rust_fn_end(&fn)`; `py_scope_begin()` →
   `py_scope_end(...)`.
2. **A declaration returns the value later references reuse** — `rust_let` returns a
   `RustVal`, `cpp_new` a `CppObj`, `py_str` a `PyVal`; never a re-typed literal.
3. **One tag per logical value.** The "tag = variable name" discipline from
   `c_funcs.h` is preserved; language runtime headers (refcount, type id, vtable
   pointer) get their own stable tags (`"refcount"`, `"typeid"`, `"vptr"`).
4. **Every emit flows through `c_funcs.h` → `asm_funcs.h`.** Wrappers add only
   *bookkeeping* (ownership state, refcount deltas, method tables); all bytes come
   from existing emitters.
5. **Driver indentation mirrors structure** — one level per function / `if` / data
   section.

### Common lowering vocabulary

| Concept | Lowered with |
| --- | --- |
| function / method | `c_begin_function` / `c_end_function` (+ `this`/`env` as param 0) |
| local value | `c_dup` / `c_into` / `c_global` (`write_init/replace/set_mov`) |
| call + result binding | `c_call_ext` / `c_call_proc_void` (`write_*_call`, rax bound) |
| branch / loop | `c_if_*` / `c_end_if` / `c_label` / `c_goto` |
| object / box / env | `c_struct_*` auto-layout (`write_data_memory_layout`) |
| heap alloc / free | extern calls to `HeapAlloc` / `HeapFree` (via `c_extern`) |
| abort / panic | extern call to `ExitProcess` with a distinguished code |

## 3. Generation-time vs runtime error checking

A deliberate teaching contrast runs through the five wrappers:

- **Rust and C++ catch errors at generation time.** The borrow checker and type
  system become C-side invariants: `rust_move(&src)` sets `src.moved`, and a later
  `rust_use(src)` aborts generation ("use after move"), mirroring how the tag
  dictionaries already abort on misuse. Nothing is emitted for the erroneous path.
- **C#, Python, and JavaScript check at runtime.** Dynamic typing, boxing/unboxing
  casts, and prototype lookups lower to *runtime branches* that raise or return a
  sentinel — an `InvalidCastException` branch, a `typeid` mismatch, a prototype
  chain terminating in `undefined`. The dynamism is made explicit in the emitted
  assembly rather than resolved away.

## 4. Per-language infrastructure

Each `*_funcs.h` is **self-contained** — there is no shared `lang_runtime.h`. The
recurring patterns are re-implemented (kept small) inside each header:

- **Heap + process helpers.** Each header declares its own `c_extern`s for
  `GetStdHandle`, `WriteFile`, `HeapAlloc`, `HeapFree`, `GetProcessHeap`,
  `ExitProcess`, plus small alloc/free/print conveniences over `CValue`.
- **Scope / cleanup engine.** Rust `Drop`, C++ destructors, C# `using`/`Dispose`,
  and Python refcount cleanup are the same "register cleanups, emit LIFO at scope
  end" pattern, reimplemented independently per header.
- **Vtable / method-table emitter.** C++ virtuals, C# MethodTables, and Python
  method dispatch each emit a name → proc-offset table via `c_ptr_data`
  (`dq offset <proc>`). JavaScript emits a sparse property list instead: three
  qwords per property (next, name id, value), also built with `c_ptr_data`.

## 5. What each wrapper exhibits

- **Rust** — move semantics and ownership (generation-time use-after-move
  detection), borrowing (`&`/`&mut` with a one-`&mut`-xor-many-`&` check), RAII
  `Drop` (LIFO scope-end), `Option`/`Result` with `?`, `match`, and `dyn Trait` fat
  pointers.
- **C++** — classes with an implicit `this`, constructors/destructors (RAII),
  references, operator overloading, virtual dispatch through a vtable, and
  generation-time template monomorphisation.
- **C#** — managed reference types vs value `struct`s, boxing/unboxing with a
  runtime type check, object headers with a MethodTable, properties as methods,
  virtual/interface dispatch, `using`/`IDisposable`, exceptions, reified generics,
  and delegates.
- **Python** — a boxed `PyObject` header (`refcount` + `typeid`), reference-count
  automation with `HeapFree` at zero, dynamic method dispatch through a per-type
  table, `list`/`dict`, and exceptions via a global `current_exc`.
- **JavaScript** — low-bit tagged values (number, string, object, null), closures
  (a fresh environment cell per `makeCounter()` call), prototype-chain lookup
  over a sparse property list, and truthy/falsy coercion.

## 6. The garbage-collection tour

Four of the five generators additionally run a **garbage-collection tour** driven by
the swappable collectors in `gc/`: Rust, C#, Python, and JavaScript (C++ is the
exception — it demonstrates deterministic RAII rather than a collector). Each of
those generators includes `gc.h`, declares a `Node` GC type, opens the collector runtime with
`gc_begin`, and calls `gc_demo`. The scripted half allocates, prints, drops,
collects, and prints again. Those addresses are not assertions. On the
conservative collector the first two objects stay reachable from callee-saved
registers, so the third is a fresh address. `gc_fuzz.h` then checks that objects
reachable from one root still hold their integers and links after `gc_collect`.
The collector and its sub-flags are chosen with `-DGC_OPTION`. What that graph
checks, and what the flag builds leave unproved, is in
[`../gc/GC.md`](../gc/GC.md) and [`../gc/GC_imp.md`](../gc/GC_imp.md). This
replaces the earlier static model in which reference objects were static globals
and nothing was reclaimed.

## 7. Build and test

`build.bat` compiles each `*_main.c`, runs it to generate its `.asm`, then
assembles, links, and runs every example, extending the same pipeline `main.c` /
`c_main.c` use. The products are written in `out/`. Because the wrappers only reorganise `write_*` / `c_*` calls, the
tag dictionaries abort the build on any type-tag mistake — a bad tag fails
generation. Each language tour prints a marker and must exit 0. `test.c` checks
that marker and the exit code on the console invocation. It does not check
intermediate numbers. The behavior program (`test/beh_tests.h`), which runs on
the window invocation and on `test.exe --behavior`, checks one field-add method
per language that has one, plus the Rust `Ok` / `Err` / `Drop` cases. The
features in section 5 outside that list are on the scripted tours, which check
the marker and the exit code. A fuzz of field counts and virtual calls, without
a collector, was not started. C# `new` and JavaScript closures allocate, and
those stay on the scripted tours. [`../TEST.md`](../TEST.md) is the coverage
report. Per-language gaps are in each `*_interface.md`.

For the four languages with a GC tour, the selected collector changes the emitted
assembly, so the output file is **option-suffixed** — `rust_output_<option>.asm`,
`csharp_output_<option>.asm`, `py_output_<option>.asm`,
`js_output_<option>.asm` — and `build.bat` walks the collector options for them.
C++ produces a single `cpp_output.asm`.
